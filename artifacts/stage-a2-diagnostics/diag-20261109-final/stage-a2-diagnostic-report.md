## Section 3: repetition penalty tracing

### Source-level definition

The canonical repetition penalty is implemented in `Components/Training/training.cpp`:

- Repetition category is calculated by `repetitionCategory(action)`.
- The penalty is applied by `repetitionPenalty(action, meaningfulResponse, tracker, consecutiveCount)`.
- The logic is:
  - if the step is meaningful, reset tracker and return `0.0f`
  - otherwise, increment a per-category run length
  - return `clamp(0.04f * max(0, consecutive - 1), 0.0f, 0.20f)`

This means:

- first no-response repeat: `0.00`
- second repeat in same category: `0.04`
- third repeat: `0.08`
- capped at `0.20`

### Reward path

The repeated-action cost is then incorporated into the overall step reward in the training loop before `agent.applyOutcome(...)` is called. The step-level reward is built from `rewardFor(...)` plus the bounded repetition penalty, then clamped and stored in the step log row.

The actual Q-learning update is then:

`updatedValue = currentValue + learning_rate * (reward + discount_factor * bestNextValue - currentValue)`

from `QLearning::update` in `Components/State-Action/state-action.cpp`.

### Distribution evidence

The q-analysis artifact includes rows such as:

- `action":"FETCH"`, `no_response_count":2`, `repetition_consecutive_count":3`, `reward":0.643...`, `valid_action_q_values` shows `FETCH` at `2.5775` while `INSIST` is `0.0`.
- Another row shows `FETCH` with `repetition_consecutive_count":1`, `reward":0.666...`, `FETCH` Q-value around `1.034`, and `INSIST` still `0.0`.

This shows the penalty is not large enough to overturn large learned values for a repeated successful or near-successful task attempt, but it is large enough to bias against repetitive no-response behaviour in the same category. For repeated failed attempts, the penalty acts as a bounded discouragement rather than a hard override.

### Assessment of scaling

The current fixed penalty is plausibly scaled as a mild discouragement mechanism:

- The cap is low enough to keep it from dominating the Q-table.
- The incremental structure still ensures a repeated behaviour loses value over time.
- It is not obviously mis-scaled by itself.

The unresolved issue is not that the penalty is obviously too large; it is that the artifact export does not include enough runtime fields to prove which repeated-action paths were actually reached in the exported run.

## Section 4: INSIST end-to-end tracing

### Request creation and ignored-response tracking

The request lifecycle is represented by the same environmental observation fields used in the training scenario generator and state encoding:

- `goal_state`
- `task_status`
- `user_status`
- `target_proximity`
- `no_response_count`
- `signal_strength`

The scenario schedule in `Components/Training/training.cpp` explicitly creates a three-step ignored-request block with `no_response_count` values 0, 1, and 2 for the same pending task.

### State encoding

`state::encode()` in `Components/State-Action/state-action.cpp` folds `no_response_count` into the state key as the final bounded radix component. This means the state space distinguishes among 0, 1, and 2 no-response counts.

### Valid-action enumeration

`isActionValidForObservation` in `Components/State-Action/action-space.h` enforces:

- `FETCH`: `task_status == 1 && target_proximity < 3`
- `INSIST`: `task_status == 1 && user_status == 0 && no_response_count >= 2`

This is the decisive gate that makes `INSIST` a delayed escalation rather than a constant valid action.

### Policy selection and execution

- `validActionsForObservation(...)` enumerates all valid actions for the current observation.
- `QLearning::chooseAction(...)` picks the highest-value valid option from the current state when a Q-value exists.
- If no Q-value is present, it falls back to the contextual fallback or the first valid action.

This means `INSIST` is available alongside the original request and any other valid actions, not as a special-case override tied only to `PLAY`.

### Reward and learning update

The reward path for ignored requests is not hardwired to a single action. The action is evaluated via context-fit and action profile. `INSIST` has a moderate task-related profile but not a dominant reward. That means it is a general escalation option with a legitimate but not guaranteed positive value once the request is repeatedly ignored.

The Q-table update follows the standard TD update from `QLearning::update`, so `INSIST` can learn a value only if it is actually contemplated and recorded in the run.

### After unanswered insist

The source does not show a dedicated abandonment or escalation state transition after an unanswered `INSIST`. The state remains defined by the same request fields and `no_response_count` semantics. There is no evidence in the retained logs of a separate persistent “abandoned” request state or a scripted post-`INSIST` action sequence. The artifacts therefore support a general escalation mechanism, but not a proven full abandonment lifecycle in the exported data.

## Section 5: minimum request-lifecycle and state information required

For persistence, escalation, and eventual abandonment to work without scripting a fixed action sequence, the minimum state needed is:

- request identity or active-task flag
- `task_status` (`pending`, `resolved`, or `abandoned`)
- `user_status` (`responding`, `ignoring`, `rejecting`, etc.)
- `no_response_count` or equivalent ignored-request streak counter
- `last_action` and timestamp for the last agent action
- `last_user_response` and timestamp
- `request_started_at` / `request_deadline` or explicit abandonment trigger
- maybe a bounded `escalation_level` or `insist_count` so the system can escalate in a general way

This is the minimum support required to persist, escalate, and eventually stop retrying without encoding a fixed action script.

## Section 6: state coverage, action coverage, Q-table support, and fallback metrics

The reporting contract in the training summaries distinguishes several different denominators:

- `unique_states_visited`: unique encoded states encountered.
- `valid_state_action_pairs_available_on_encountered_states`: for every encountered state, count the valid actions allowed by the action-validity gate; then count the union of those valid pairs.
- `q_table_supported_decision_rate`: number of decisions made when a valid Q-value existed for the current state, divided by total decisions.
- `fallback_decision_rate`: decisions taken via fallback logic (including contextual fallback or generic safe fallback) divided by total decisions.
- `state_action_coverage` is not the same as global state-space coverage; it is a coverage metric relative to encountered states only.

In the retained q-analysis summary, the mean metrics across 100 episodes are approximately:

- baseline `q_table_supported_decision_rate`: `0.973`
- baseline `fallback_decision_rate`: `0.027`
- proposed `q_table_supported_decision_rate`: `0.914`
- proposed `fallback_decision_rate`: `0.086`

This indicates that Q-table support was overwhelmingly present after learning, while fallback decisions remained comparatively minor. But it is essential not to infer global full-state coverage from these rates; they are conditional on the encountered states only.

## Proposed implementation changes (not applied)

These are the precise changes that would be required only if the team chooses to resolve the provenance/export gaps and make the delayed `INSIST` lifecycle explicitly auditable:

1. Add logging fields to the runtime export for:
   - `no_response_count`
   - `repetition_category`
   - `repetition_consecutive_count`
   - `boredom_penalty`
   - `q_table_has_valid_action_values`
   - `valid_action_q_values`
   - `final_action_after_overrides`
2. Keep the state and reward semantics unchanged while adding missing runtime serialization.
3. Add a per-request lifecycle field such as `request_state` or `escalation_level` if abandonment and escalation are to be persisted explicitly.
4. Ensure the artifact-generation path writes the same canonical build and revision metadata as the binary used to run the experiment.
5. Preserve a fresh deterministic run output bundle for the current source revision so provenance can be checked without relying on stale historical exports.

These are proposed only; no implementation was performed in this review.

## Regression-test requirements

The following tests are necessary before any future behavioural change is approved:

1. Provenance test: a training run must record the exact git revision, executable name, build mode, and command line used.
2. Export completeness test: step logs must contain all required fields for repeated-action and delayed-`INSIST` analysis.
3. Valid-action gate test: confirm `INSIST` is invalid at `no_response_count < 2` and valid at `>= 2`.
4. Repetition-penalty regression test: verify the penalty sequence is `0.00, 0.04, 0.08, capped at 0.20` for the same category without meaningful response.
5. Q-update regression test: verify the update formula and best-next-value bootstrap remain unchanged.
6. Coverage-metric regression test: verify state coverage, state-action coverage, Q-table support, and fallback rates are measured using their distinct denominators.
7. Deterministic-seed test: identical seeds must generate identical scenario schedules; different seeds must produce distinct schedules.
